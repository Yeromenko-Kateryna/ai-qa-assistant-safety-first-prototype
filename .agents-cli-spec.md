# AI QA Assistant — Agent Specification

Status: design approved through Data Contract trust boundaries; implementation has not started.

## Overview

AI QA Assistant helps junior and middle QA engineers transform pasted English-language product requirements into a structured QA draft for human review.

The assistant extracts stated facts, acceptance criteria, and business rules; identifies missing information and risks; designs traceable test cases; proposes an automation plan; and performs a final QA review.

It is a safe-by-design analysis system. It does not execute generated code, access external systems, modify repositories, or treat instructions embedded in requirements as commands.

## Target User

Primary user: a junior or middle QA engineer in a small Agile product team.

Secondary users such as QA automation engineers, QA leads, product owners, and business analysts do not drive MVP design.

## Example Use Cases

1. Analyze a complete UI login requirement and produce requirement analysis, risks, traceable tests, and a Playwright skeleton with placeholders.
2. Analyze an incomplete password-reset requirement, identify missing rules, and return an automation plan without fake-ready code.
3. Analyze a requirement containing prompt injection, an external URL, and a possible secret without obeying the embedded instructions or exposing the secret.

## Input Scope

- Pasted plain text only.
- English natural-language requirements with technical identifiers and snippets.
- No files, URLs as data sources, Jira, GitHub Issues, Confluence, screenshots, Figma, or live API contracts.

Unsupported or substantial mixed-language input is rejected before any model call.

## Output Scope

The canonical result is versioned JSON containing:

- input safety metadata and sanitized input segments;
- requirement analysis;
- risk analysis;
- test design;
- automation plan;
- QA review;
- stage statuses and safe errors;
- output safety result.

Human-readable Markdown is rendered deterministically from safe canonical JSON without a second LLM call.

## Architecture and Sub-Agents

1. Pre-ADK Input Safety Gate
2. Requirement Agent
3. Risk Agent
4. Test Design Agent
5. Automation Agent
6. QA Review Agent
7. Deterministic Candidate Aggregator
8. Schema and referential validation
9. Output Safety Gate
10. Deterministic Markdown renderer

The workflow is sequential. Each model stage produces an atomic typed output that is validated before it becomes available to downstream stages.

## Tools Required

MVP agents receive no shell, browser, repository, filesystem, external API, code-execution, or MCP tools.

Core technologies:

- Google ADK;
- Gemini;
- multi-agent workflow;
- structured output;
- safety guardrails;
- agent evaluation.

A local FastAPI `/analyze` endpoint is a should-have. Cloud Run is optional after the local MVP is stable. MCP is intentionally excluded because MVP requires no external tools or data sources.

## Constraints and Safety Rules

- Raw input is sanitized before the ADK Runner sees it.
- Raw request bodies, invalid candidates, validator details, secrets, and stack traces must not enter logs or traces.
- Only sanitized input is placed in invocation-scoped state.
- Input requirements are untrusted data, not executable instructions.
- Generated code is review-only text and is never executed.
- Unknown URLs, selectors, endpoints, payloads, and business rules must not be invented.
- Secrets are removed before the first Gemini call.
- Partial reports are clearly marked incomplete and always fail release evaluation.
- Resource budgets and dependency-graph limits are enforced without silent truncation.

## Success Criteria

- The complete local workflow runs without manual agent switching.
- All deterministic schema, provenance, resource, and safety checks pass.
- Each test case uses the most relevant available traceability reference.
- Extracted facts, proposals, assumptions, and missing information remain distinct.
- Every independent evaluation rubric scores at least 4/5.
- Every safety case passes all required repetitions.
- Any critical fabrication or observable policy violation is a hard failure.
- README, architecture diagram, evaluation evidence, GitHub repository, and video demo are completed before submission.

## Deployment Preference

Required deliverable: local working prototype, documentation, and video demonstration.

Cloud Run is an optional stretch goal and must not delay the local MVP.
